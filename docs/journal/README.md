# 学习心得日志（Journal）

这个目录记录**你自己的理解过程**，不是操作手册。

操作手册放在 `docs/handoff/`（给 AI 和未来的自己看"项目现在是什么状态"）；
这里放"我是怎么想明白的"——这两件事完全不同，别混。

---

## 为什么值得写

1. **对抗遗忘**：三周后你会忘记今天为什么选了异步、为什么 `localhost` 不通。
   笔记不是给现在看的，是给"已经忘光了的你"看的。
2. **面试素材**：面试官问"你遇到过什么困难"，你能立刻答出具体场景和推理过程，
   比"我做过一个 RAG 项目"强十倍。**心得日志就是你的题库。**
3. **暴露真正的盲区**：能把一个概念讲清楚，才算真懂。写不出来的地方就是没懂的地方。

---

## 命名规范

```
YYYY-MM-DD-主题.md
```

例：

```
2026-10-19-docker数据到底在哪.md
2026-10-20-为什么第一个功能是health检查.md
2026-10-22-uv为什么让pytest用错了解释器.md
```

一个主题一个文件。**不要写"日记"（10-19 流水账），要写"专题"（一个问题的完整思考）。**

---

## 模板

```markdown
# 主题

## 1. 我原来的理解
（先把错误理解写下来，这比正确答案更有价值）

## 2. 是什么让我发现不对
（哪条命令、哪个报错、哪个观察）

## 3. 现在的理解
（用自己的话，不要抄文档）

## 4. 如果给别人讲，我会怎么说
（三句话以内）

## 5. 还没想明白的
- 
```

第 1 节和第 4 节最重要。第 1 节记录"认知的起点"，第 4 节检验"是否真的懂"。

---

## 写什么 / 不写什么

| 写 | 不写 |
|---|---|
| 我原本以为 X，实际是 Y，因为… | 今天执行了 docker compose up（操作手册，进 handoff） |
| 这个概念和我知道的 Java 那套如何对应 | 完整的命令清单（git 里都有） |
| 我踩的坑和发现它的过程 | 大段抄来的官方文档 |
| 还没想明白的问题 | 已经理解得很透的东西（浪费时间） |

---

## 建议的第一篇

今天的对话里有一个非常好的题目：

> **"数据到底存在哪？为什么放在 Docker 里，还是 `curl 127.0.0.1`，但它又不在我的 C 盘目录里？"**

这个问题你已经从"完全不懂"走到了能自己解释。把它写下来——**这是这个项目里第一个真正的概念突破。**
