# 个人技术百科：技术设计评审与实施基线

- 版本：1.0
- 状态：阶段二技术设计评审基线
- 目标：不过度设计，尽快交付可运行、可测试、可备份的个人知识管理应用。

## 1. 评审结论

现有方案可行，采用模块化单体，不采用微服务。开始编码前明确三项边界：

1. **第一版包含基础 RAG。** 使用 PostgreSQL 全文检索查找知识，将实际检索结果提供给模型生成回答，并展示真实条目和来源。语义向量检索与 `pgvector` 作为后续增强，不阻塞首个可用版本。
2. **来源与知识条目独立建模。** 一份来源可以支持多个知识条目，一个知识条目也可以关联多个来源；通过关联表表达多对多关系。
3. **预留知识空间。** 核心业务数据从第一版起预留 `workspace_id`，个人使用时只创建一个默认空间。注册登录、配额和多用户权限延后；邀请他人使用前必须实现并验证认证、服务端授权和空间隔离。

## 2. 架构与技术栈

- 前端：React + TypeScript + Vite
- API 与业务层：Python + FastAPI
- 数据访问：SQLAlchemy
- 数据库迁移：Alembic
- 数据库：PostgreSQL
- 文件解析：PyMuPDF，以及 Markdown/TXT 解析工具
- 模型调用：独立的模型服务适配层
- 测试：pytest、前端测试工具与必要的端到端测试
- 运行与部署：Docker Compose

采用模块化单体，逻辑模块包括知识导入、知识管理、知识检索、AI 助手、文档解析、模型服务适配、数据访问、配置与安全。新增输入方式复用整理保存流程；新增检索方式不应侵入知识管理；模型供应商格式不应扩散到业务层。

## 3. 核心数据模型

### KnowledgeEntry（知识条目）

- `id`：唯一标识
- `workspace_id`：所属空间
- `title`：标题
- `content`：用户确认保存的正文
- `summary`：可空摘要
- `category`：可空主要分类
- `created_at`、`updated_at`：创建与更新时间

标签可以在初版用简单、可测试的方式实现；避免复杂标签体系阻塞首版。

### KnowledgeSource（知识来源）

- `id`
- `workspace_id`
- `source_type`：`file`、`pasted_text`、`url` 等
- `source_name`
- `source_url`：可空
- `file_path` 或文件存储标识：可空
- `source_excerpt`：可空原文片段
- `created_at`

使用 `KnowledgeEntrySource` 关联表连接知识条目与来源。原始输入/来源与用户确认后的知识正文应有清晰区别。AI 摘要或修改建议不能未经确认覆盖知识正文。第一版可以不实现完整版本历史，但必须先预览、再确认。

### KnowledgeRelation（知识关联）

- `id`
- `workspace_id`
- `source_entry_id`
- `target_entry_id`
- `relation_type`
- `created_at`

初版支持建立、查看和删除关联即可；图形化知识地图延后。需避免自关联，并为重复关联定义唯一性规则。

### Workspace（知识空间）

第一版创建一个默认空间，并在核心业务数据中保存 `workspace_id`。暂不实现多用户账号体系。所有读写必须在服务端限定空间范围，不能只依赖前端隐藏数据。

### 检索索引

检索索引属于可重建的派生数据，不是知识的权威来源。第一版使用 PostgreSQL 全文检索；后续根据真实搜索效果和数据规模评估 Embedding 与 `pgvector`。

## 4. 核心数据流

### 导入与整理

1. 接收 PDF、Markdown、TXT 或粘贴文本。
2. 校验输入并提取文本；失败时说明原因，保留可重试状态。
3. 记录来源信息。
4. 可选调用模型生成标题、摘要、关键词和分类建议。
5. 用户预览、修改并确认。
6. 保存知识条目及来源关联。
7. 更新或重建相关检索索引。

AI 不可用时，用户仍能手动创建、编辑、保存和关键词检索。

### 检索与问答

1. 接收用户问题。
2. 使用 PostgreSQL 全文检索取得候选知识。
3. 将实际检索到的条目内容与来源交给模型生成回答。
4. 展示回答及对应知识条目/来源。
5. 没有可靠检索结果时，明确说明，不伪造来源。

### 更新已有知识

1. 找出可能相关的旧条目。
2. 生成并展示新增内容或修改建议。
3. 用户确认前不修改现有正文。
4. 确认后保存更新并保留来源关联；取消或失败不破坏旧内容。

## 5. 测试方案

### 单元测试
覆盖输入校验、解析错误处理、业务规则、AI 输出校验、超时与异常处理。模型调用应可用 mock 替代，普通测试不依赖真实 API。

### 集成测试
使用独立测试数据库，覆盖数据保存/读取、来源关联、知识关联、事务回滚、数据库迁移、检索结果和空间范围过滤。

### 端到端测试
至少覆盖：
- 创建、编辑、保存、搜索并查看知识
- 导入文件并确认 AI 整理建议
- 查看来源
- 预览并确认更新
- 取消更新后正文不变

### 部署与恢复测试
验证容器重启后数据仍存在、备份可以恢复、迁移可以执行、模型服务不可用时基础功能仍可用。必须实际执行恢复演练。

## 6. 部署与安全

- 使用 Docker Compose 管理前端、API、PostgreSQL。
- 数据库使用持久化卷；需要保留的原始文件使用独立持久化存储。
- 数据库与必要的上传文件都纳入备份策略。
- 使用 Alembic 管理数据库迁移。
- 提供 `.env.example`，不提交真实 `.env`、API 密钥或私人知识。
- 对模型调用设置超时和错误处理。
- 日志不输出密钥；默认不把整个知识库发送给模型。
- 个人部署稳定后再考虑云部署。
- 对外开放前完成认证、服务端授权、空间隔离、HTTPS、配额与安全测试。

## 7. 第一版范围冻结

### 必须实现
- PDF、Markdown、TXT 和粘贴文本导入
- 手动创建、查看、编辑、保存知识
- AI 标题/摘要/关键词/分类建议，并由用户确认
- 关键词检索
- 基础 RAG 问答，答案展示真实知识条目和来源
- 相关/重复条目提示
- 确认式更新
- 来源追溯
- 错误反馈、数据持久化、备份与恢复说明

### 延后实现
- 自动抓取网页正文、整仓 GitHub 解析、OCR
- 复杂知识图谱、多 Agent 工作流
- 注册登录、熟人多用户空间管理与配额
- 图形化知识地图
- 独立向量数据库、复杂缓存和任务队列
- 完整的知识版本历史系统

## 8. 实施顺序

1. 初始化仓库、前后端骨架、配置、Docker Compose 与健康检查。
2. 建立 PostgreSQL 模型和 Alembic 迁移。
3. 完成知识 CRUD 与关键词检索。
4. 完成文件解析、来源记录与导入流程。
5. 完成 AI 整理建议与确认式更新。
6. 完成基础 RAG 与来源展示。
7. 完成回归测试、备份恢复演练和个人部署。
8. 根据真实使用反馈修复问题，再规划熟人试用。

## 9. 评审验收条件

- 架构与技术栈已固定；
- 核心数据关系与来源追溯规则明确；
- 第一版基础 RAG 的范围明确；
- AI 更新必须由用户确认；
- 数据持久化、备份和恢复有明确方案；
- 多用户能力只做空间字段预留，不提前扩张为复杂账号系统；
- 第一版范围与实施顺序已经冻结。
