## D-001 采用模块化单体，不做微服务

- **背景**：个人项目，只有 1 个开发者，用户数是"自己 + 几个熟人"
- **决策**：单进程后端 + Docker Compose 编排少量服务
- **理由**：微服务的收益（独立扩容、独立部署、团队并行）在这个规模下全部为零，成本（网络调用、分布式事务、运维复杂度）全部要付
- **代价**：将来如果真的要拆分，需要有清晰的模块边界
- **替代方案**：微服务 —— 否决，是典型的过度设计

## D-002 第一版包含基础 RAG，但不引入向量数据库

- **背景**：需求要求"用自然语言问题找回知识"
- **决策**：用 PostgreSQL 全文检索取候选 → 把**实际检索结果**交给模型生成回答 → 展示真实条目与来源。`pgvector` 延后
- **理由**：全文检索零额外依赖、可解释、可调试；语义检索的收益要等真实数据量和真实问题出现后才能验证
- **代价**：召回率不如向量检索，尤其是同义表述
- **替代方案**：直接上 `pgvector` —— 否决，会把首版拖进 embedding 维度、索引参数、成本调优的细节里
- **后续触发条件**：真实使用中反复出现"知识明明在但搜不到"，再引入

## D-003 预留 `workspace_id`，但不做账号体系

- **背景**：需求写明了熟人试用阶段要做数据隔离，但第一版只服务一个人
- **决策**：核心业务表从第一版起就带 `workspace_id`，个人使用只创建一个默认空间；不做注册登录
- **理由**：加字段很便宜，事后给已有数据补维度很贵
- **代价**：现阶段 `workspace_id` 是"无用字段"，容易被人忘记在服务端强制过滤
- **硬性要求**：所有读写**必须**在服务端按 `workspace_id` 限定，绝不能靠前端隐藏

## D-004 后端用 Python + FastAPI，而不是继续用 Java + Spring

- **背景**：作者熟悉 Java + Spring，本项目核心却是 AI 能力
- **决策**：Python + FastAPI
- **理由**：**唯一决定性理由是 AI 生态**。PDF 解析（PyMuPDF）、LLM SDK、embedding、文本处理在 Python 侧最完整；Java 侧要么滞后，要么需要额外起一个 Python 子服务
- **代价**：失去编译期类型检查；团队协作型项目的成熟方案在 Python 侧要自己搭
- **替代方案**：
  - Spring Boot —— 否决，AI 部分会被迫引入跨语言调用
  - Django —— 否决，它的 admin/ORM 优势对本项目不重要，而 async 支持弱于 FastAPI
- **注**：如果这个项目将来变成"纯知识管理、不含 AI"，Java 反而是更好的选择。**选型服务于需求。**

## D-005 用 uv 管理 Python 依赖，禁用 pip / conda

- **背景**：本机已有 Anaconda 3.9，PATH 里排得很靠前
- **决策**：项目内一切 Python 操作走 `uv`（`uv add` / `uv sync` / `uv run`），Python 解释器由 uv 管理
- **理由**：`uv.lock` 提供精确版本锁定；`uv run` 自带环境准备；速度远快于 pip；不污染系统环境
- **代价**：团队里必须统一用 uv，否则会与 pip 混用
- **踩坑记录**：`uv run pytest` 在 venv 中找不到命令时会**静默回落 PATH**，导致用了 Anaconda 的 pytest。所以统一写成 `uv run python -m pytest`

## D-007 数据库数据用命名卷，不用 bind mount

- **背景**：Docker 有两种持久化方式
- **决策**：`pgdata:/var/lib/postgresql/data`（命名卷）
- **理由**：
  1. **性能**：Windows 上 bind mount 到 NTFS 会让 PG 的小文件 I/O 慢一个数量级
  2. **正确性**：PG 依赖文件系统语义（`fsync`、目录锁），跨文件系统映射有损坏风险
  3. **安全性**：命名卷天然不会被 git 看见
- **代价**：不能直接用资源管理器浏览数据文件，备份必须用 `pg_dump`
- **反例（将来会用 bind mount 的场景）**：用户上传的 PDF —— 放 `./data/uploads`，好处是能直接看见、能 gitignore、容器重建不丢

## D-011 采用全异步数据库访问（SQLAlchemy async + asyncpg）—— 已决定

- **背景**：M1 开始引入 ORM，这个决定会贯穿所有后续代码
- **决策**：**全异步**。`create_async_engine` + `AsyncSession` + `asyncpg`，迁移用 Alembic 的 async 模板
- **理由**：
  1. 项目核心是 AI。一次模型调用是数秒级 I/O 等待，同步会把线程全程占住
  2. FastAPI 生态（LLM SDK、httpx）原生 async，混用要时刻提防"在 async 里调用同步阻塞代码"，而那种错误会卡死整个事件循环
  3. 若先做同步，M4 做 RAG 时要返工所有 repository 函数 + endpoint + Alembic 配置
- **代价**：
  1. 关系属性**不能懒加载**，必须 `selectinload()` 显式预加载，否则报 `MissingGreenlet`
  2. `AsyncSession` 不能跨协程共享，必须"每请求一个 session"
  3. Alembic 要用 `-t async` 模板，并在 `env.py` 里处理 `run_sync`
- **替代方案**：同步 + `psycopg` —— 更接近作者的 Spring 经验、上手更快。否决原因：作者目标是"学对 + 不走回头路"，而不是最快看到结果
- **状态**：**已决定（2026-10-19）**

## D-013 ruff 规则集显式声明，并忽略"形近字符"类规则

- **背景**：一次 CI 失败暴露 56 个 lint 错误。其中 14 个是真实问题（import 排序、过时语法、`Depends` 默认参数），另外 53 个是 `RUF002/RUF003` 在抱怨中文全角标点
- **决策**：
  1. **显式声明** `select = ["E", "F", "I", "UP", "B", "RUF"]`，不依赖 ruff 默认值
  2. `extend-exclude = ["alembic/versions"]` —— Alembic 生成的迁移文件不参与风格检查
  3. `ignore = ["RUF001", "RUF002", "RUF003"]` —— 注释与文档字符串使用中文，全角标点是正确书写
  4. 依赖注入统一用 `Annotated[AsyncSession, Depends(get_session)]`，避免 `B008`
- **理由**：
  - 默认值会随 ruff 版本变化。某天升级 ruff 突然爆一堆错，你无法判断是自己改坏了还是规则变了
  - 生成代码不是我们写的，用我们的风格规则去要求它没有意义
  - `RUF001-003` 假设"代码里只有英文"，其真实目的是防止西里尔字母伪装拉丁字母（安全攻击）。中文项目不适用
- **代价**：中文注释的代码在纯英文团队里会显得不一致
- **替代方案**：把 Python 注释全部改成英文 —— 否决。注释是学习产物，中文表达更精确；且 `docs/` 全为中文，混排反而割裂
- **副作用记录**：`RUF100`（无用 noqa）很有价值，它一次性发现 3 个"防根本不存在的错"的安慰剂注释
- **状态**：**已决定（2026-10-21）**

## D-014 测试用真实 PostgreSQL + 每测试一事务回滚

- **背景**：M1-4 引入自动化测试，必须解决三件事：① 不能污染开发库 ② 测试之间必须隔离 ③ CI 里也要能跑
- **决策**：
  1. 独立的测试库 `knowledge_test`（与开发库 `knowledge` 分开）
  2. 用**真实 PostgreSQL**（CI 里用 `services: postgres` 起一个容器），**不用 SQLite**
  3. 每个测试跑在一个外层事务里，`AsyncSession(bind=conn, join_transaction_mode="create_savepoint")`；测试结束 `rollback`，表结构保留
  4. 通过 `app.dependency_overrides[get_session]` 注入测试 session，**不改生产代码**
  5. 用 `httpx.AsyncClient` + `ASGITransport(app=app)`，进程内直连 ASGI 应用，不起真实服务、不占端口
- **理由**：
  - SQLite 与 PostgreSQL 在 `Uuid`、`timestamptz`、`server_default now()`、约束行为上都不同。**用 SQLite 测一个 PG 项目，等于在测一个不存在的系统**
  - `join_transaction_mode="create_savepoint"` 是必要的：接口内部会 `session.commit()`，没有它 commit 会提交外层事务，回滚机制失效
  - `dependency_overrides` 让"换数据库"只发生在测试配置里，生产代码零改动
  - ASGITransport 让 7 个测试在 0.8 秒内跑完
- **代价**：
  - CI 里多一个 service 容器，job 启动多约 10 秒
  - 本地必须先手动建一次 `knowledge_test` 库
  - session 级异步夹具会撞上 pytest-asyncio 的事件循环作用域问题，所以建表夹具用**同步夹具 + `asyncio.run`** 绕开
- **替代方案**：
  - SQLite 内存库 —— 否决，与生产行为不一致
  - 每个测试重建表（`drop_all`/`create_all`）—— 否决，慢且易并行冲突
- **验证手段**：写了一个"元测试" `test_tests_are_isolated`，它断言"上一条测试什么都没留下"。隔离机制如果失效，这个测试会失败
- **状态**：**已决定（2026-10-21）**

## D-015 API 语义：PATCH 部分更新、统一 404、契约层与 ORM 分离

- **背景**：M1-3 写 CRUD 时需要定几个接口语义，这些一旦定下、前端依赖之后就很难改
- **决策**：
  1. 更新用 **`PATCH`** 而不是 `PUT`，实现上用 `payload.model_dump(exclude_unset=True)` 只写客户端真正传了的字段
  2. "资源不存在"和"资源存在但属于别的 workspace"**都返回 404**，不区分 403
  3. 请求/响应体用独立的 Pydantic 模型（`schemas/`），**不复用 ORM 模型**
  4. 列表接口在**服务端**按 `workspace_id` 过滤，不依赖前端
- **理由**：
  - `PUT` 的语义是整体替换。用户只想改分类时，`PUT` 会强迫客户端传全部字段，漏传就把数据抹了
  - 若"存在但无权访问"返回 403，攻击者可通过 403/404 的差异探测出哪些 id 真实存在。统一 404 信息量为零
  - ORM 模型描述"数据库长什么样"，可能含内部字段（软删除标记、内部备注）；直接当响应体用迟早泄露
  - 需求文档硬性要求：所有读写必须在服务端限定空间范围
- **代价**：
  - `PATCH` + `exclude_unset` 比 `PUT` 多一层理解成本
  - 契约层要维护两套字段定义，改字段要动两处
- **状态**：**已决定（2026-10-21）**

## D-016 M2 文件解析的三条范围决策（原文分离 / 扫描件提示 / 保守过滤）

- **背景**：需求文档只写了"支持 PDF、Markdown、TXT"，没写这三件事怎么办。而它们直接决定解析器的返回结构和存储设计，写在代码之后返工成本高
- **决策**：
  1. **原文与精炼正文分离存储**：`knowledge_sources.extracted_text` 存**完整提取文本**（解析结果的原始快照），`knowledge_entries.content` 只存**用户确认后的精炼版**
  2. **扫描版 PDF 要明确区分提示**：识别"文档没有文字层"这种情况，向用户说明原因（需要 OCR 才能解析），**不是技术报错，也不是静默建空条目**
  3. **噪音做保守规则过滤**：只过滤"在多数页面重复出现且长度很短"的行（页眉/页脚/页码），不做激进的启发式清洗
- **理由（作者原话）**：
  - Q1：全文入库会增加成本（AI token 消耗、检索噪音），截断又会丧失一部分功能 → **分离存储同时满足两端**，也符合需求文档"原始输入必须保留"的硬要求
  - Q2：希望用户体验更好——用户需要知道"为什么没提取出来"和"接下来该怎么办"，而不是看到一个吓人的技术错误
  - Q3：选择相对保守的方法，宁可留下噪音，也不要误删正文
- **连带影响**：
  - `knowledge_sources` 需要 `extracted_text` 字段（M2-1 一并建）
  - 解析器返回值必须能表达**三种状态**：成功 / 成功但内容为空（无文字层）/ 失败（附可读原因）
  - 需要定义"短行"和"重复"的具体阈值（M2-2 定，初值建议：长度 < 80 字符，且在 ≥ 30% 的页面出现）
- **待定**（后续里程碑再定，不在 M2-1 阻塞）：
  - 单文件大小上限、页数上限 → M2-3 上传接口时定
  - 是否给用户"查看来源全文"的入口 → M3 前端时定
- **替代方案**：
  - 全文直接进 `content`：否决，会让 AI 总结 token 爆掉，且让"用户确认过的内容"失去意义
  - 截断入库：否决，丢失的内容用户不可见，违背"可追溯"
  - 本期不做噪音过滤：否决，噪音会一直污染 M4 的检索质量
- **状态**：**已决定（2026-10-21）**

## D-017 PDF 解析用 PyMuPDF，项目许可证定为 AGPL-3.0

- **背景**：`pymupdf 2.0` 的许可证是 **AGPL-3.0 或 Artifex 商业授权（双许可）**。AGPL 有传染性：把项目作为网络服务提供给他人时，须以 AGPL 公开整个项目源码
- **决策**：使用 PyMuPDF，并为项目选定 **AGPL-3.0**
- **理由**：
  1. PyMuPDF 的文本提取质量显著优于 alternatives（尤其双栏论文、复杂版式），而提取质量直接决定 M4 检索质量
  2. **仓库本来就是 public**，AGPL 的"必须开源"义务对作者成本接近零
  3. 作者目标是自己使用 + 熟人试用 + 作品集，不涉及闭源商业化
- **代价**：放弃闭源可能；若将来要闭源，需购买 Artifex 商业授权
- **替代方案**：
  - `pypdf`（BSD-3-Clause）—— 许可证最宽松、纯 Python、镜像更小；但复杂版式会提取成乱序文本
  - `pdfplumber`（MIT，基于 pdfminer.six）—— 许可证宽松、质量居中；但慢且内存占用高
- **降低风险的手段**：解析器层做成可插拔（`ParseResult` + 按后缀分发），换 PDF 实现只需改 `app/parsers/pdf.py` 一个文件
- **状态**：**已决定（2026-10-22）**

## D-018 扫描件判定标准：平均每页少于 25 字符

- **背景**：D-016 要求区分"解析失败"和"文档本来就没有文字层"。需要一个可量化、可测试的判定规则
- **决策**：`提取文本总字符数 / 页数 < 25` → 判定为 `EMPTY`（无文字层），而不是 `OK` 或 `FAILED`
- **理由**：
  - 用**全文平均**而不是**逐页判定**：单页可能是封面、插图页或章节分隔页，逐页判定会误报；全文平均对整份文档更稳
  - 25 的门槛依据：正常数字文档平均每页数百到数千字符；扫描件接近 0；纯图片页可能只有页眉几个字符
- **代价**：极少数"图文混排、文字极少"的文档会被判定为无文字层（提示需要 OCR，属于可接受的误报方向——误报为"需要 OCR"比误报为"解析成功但内容为空"体验更好）
- **状态**：**已决定（2026-10-22）**

## D-019 M2 实施顺序调整：先文本、后 PDF（最小可用优先）

- **背景**：原计划 M2-2 直接做 PDF 解析。但作者的真实目标是"先让自己用起来"，而 PDF 是 M2 里最难的输入（需要重依赖 + 扫描件检测 + 噪音过滤）
- **决策**：调整顺序为 文本解析 → 文本入库闭环 → 文件上传 → PDF 解析 → 噪音过滤
- **理由**：
  - **walking skeleton 原则**：先用最简单的路径打通"输入 → 解析 → 入库 → 可查询"整条链路，再往管道里塞复杂输入
  - 作者手上已有大量 Markdown 笔记，文本入库后**当天就能真实使用**；PDF 只有在"天天在用"之后才有价值
  - 链路短时排查成本低：出问题时能区分是"解析错"还是"入库错"
  - 文本解析**零外部依赖**（不引入 PyMuPDF），M2-2 可以在没有任何新依赖的情况下完成
- **代价**：PDF 支持推迟；但前面所有基础设施（解析器层、来源模型、上传接口）届时已就位，PDF 只是"再加一个解析器实现"
- **状态**：**已决定（2026-10-22）**

## D-020（待定）删除条目后，来源与磁盘文件的处理方式

- **背景**：M2-4 实测时发现——删除一个 `knowledge_entry` 时，`knowledge_entry_sources` 里的关联行
  会因 `ON DELETE CASCADE` 自动消失，但 **`knowledge_sources` 的记录和磁盘上的文件会残留**，
  成为没有任何条目引用的"孤儿来源 + 孤儿文件"
- **三个候选方案**：

  | 方案 | 效果 | 代价 |
  |---|---|---|
  | A. 删条目时连带删来源（若已无其它条目引用） | 数据干净、磁盘不膨胀 | 删掉的知识无法追溯，与"原始输入必须保留"的规则冲突 |
  | B. 来源保留，提供"清理无引用来源"的维护操作 | 保留可追溯性 | 需要额外实现清理逻辑；孤儿会暂时存在 |
  | C. 不处理 | 最简单 | 数据库和磁盘会持续积累垃圾，长期部署后无法收拾 |

- **倾向**：**B**——需求文档把"原始输入与来源必须保留"列为不可违背的规则，
  所以不应该在删除条目时把来源一并销毁；但需要给用户一个显式的清理入口。
- **待定原因**：这个决定会影响 M3（前端"删除条目"的交互）和 M5（备份/清理脚本），
  在进入 M3 之前必须拍板
- **状态**：**待决定**
