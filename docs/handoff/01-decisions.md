# 技术决策记录（ADR）

> **用途**：记录"为什么这样选"，而不是"选了什么"。技术栈写在 `00-project-state.md`，
> 本文件记录**取舍理由**和**被否决的选项**。
>
> **维护规则**：只追加，不修改历史条目。改变主意就新增一条并注明取代了哪条。
> 格式：背景 → 决策 → 理由 → 代价 → 替代方案（及为何否决）

---

## D-001 采用模块化单体，不做微服务

- **背景**：个人项目，只有 1 个开发者，用户数是"自己 + 几个熟人"
- **决策**：单进程后端 + Docker Compose 编排少量服务
- **理由**：微服务的收益（独立扩容、独立部署、团队并行）在这个规模下全部为零，成本（网络调用、分布式事务、运维复杂度）全部要付
- **代价**：将来如果真的要拆分，需要有清晰的模块边界
- **替代方案**：微服务 —— 否决，是典型的过度设计

## D-002 第一版包含基础 RAG，但不引入向量数据库

- **背景**：需求要求"用自然语言问题找回知识"
- **决策**：用 PostgreSQL 全文检索取候选 → 把**实际检索结果**交给模型生成回答 → 展示真实条目与来源。`pgvector` 延后
- **理由**：全文检索零额外依赖、可解释、可调试；语义检索的收益要等真实数据量和真实问题出现后才能验证
- **代价**：召回率不如向量检索，尤其是同义表述
- **替代方案**：直接上 `pgvector` —— 否决，会把首版拖进 embedding 维度、索引参数、成本调优的细节里
- **后续触发条件**：真实使用中反复出现"知识明明在但搜不到"，再引入

## D-003 预留 `workspace_id`，但不做账号体系

- **背景**：需求写明了熟人试用阶段要做数据隔离，但第一版只服务一个人
- **决策**：核心业务表从第一版起就带 `workspace_id`，个人使用只创建一个默认空间；不做注册登录
- **理由**：加字段很便宜，事后给已有数据补维度很贵
- **代价**：现阶段 `workspace_id` 是"无用字段"，容易被人忘记在服务端强制过滤
- **硬性要求**：所有读写**必须**在服务端按 `workspace_id` 限定，绝不能靠前端隐藏

## D-004 后端用 Python + FastAPI，而不是继续用 Java + Spring

- **背景**：作者熟悉 Java + Spring，本项目核心却是 AI 能力
- **决策**：Python + FastAPI
- **理由**：**唯一决定性理由是 AI 生态**。PDF 解析（PyMuPDF）、LLM SDK、embedding、文本处理在 Python 侧最完整；Java 侧要么滞后，要么需要额外起一个 Python 子服务
- **代价**：失去编译期类型检查；团队协作型项目的成熟方案在 Python 侧要自己搭
- **替代方案**：
  - Spring Boot —— 否决，AI 部分会被迫引入跨语言调用
  - Django —— 否决，它的 admin/ORM 优势对本项目不重要，而 async 支持弱于 FastAPI
- **注**：如果这个项目将来变成"纯知识管理、不含 AI"，Java 反而是更好的选择。**选型服务于需求。**

## D-005 用 uv 管理 Python 依赖，禁用 pip / conda

- **背景**：本机已有 Anaconda 3.9，PATH 里排得很靠前
- **决策**：项目内一切 Python 操作走 `uv`（`uv add` / `uv sync` / `uv run`），Python 解释器由 uv 管理
- **理由**：`uv.lock` 提供精确版本锁定；`uv run` 自带环境准备；速度远快于 pip；不污染系统环境
- **代价**：团队里必须统一用 uv，否则会与 pip 混用
- **踩坑记录**：`uv run pytest` 在 venv 中找不到命令时会**静默回落 PATH**，导致用了 Anaconda 的 pytest。所以统一写成 `uv run python -m pytest`

## D-006 数据库跑在 Docker 里，不装在本机

- **决策**：PostgreSQL 16-alpine 作为 Compose 服务
- **理由**：本机不需要装数据库；换机器 / 换服务器只需 `docker compose up -d`；版本被镜像 tag 固定
- **代价**：多一层容器概念；数据不能直接用资源管理器打开
- **替代方案**：本机安装 PostgreSQL —— 否决，会与"可复现"目标冲突

## D-007 数据库数据用命名卷，不用 bind mount

- **背景**：Docker 有两种持久化方式
- **决策**：`pgdata:/var/lib/postgresql/data`（命名卷）
- **理由**：
  1. **性能**：Windows 上 bind mount 到 NTFS 会让 PG 的小文件 I/O 慢一个数量级
  2. **正确性**：PG 依赖文件系统语义（`fsync`、目录锁），跨文件系统映射有损坏风险
  3. **安全性**：命名卷天然不会被 git 看见
- **代价**：不能直接用资源管理器浏览数据文件，备份必须用 `pg_dump`
- **反例（将来会用 bind mount 的场景）**：用户上传的 PDF —— 放 `./data/uploads`，好处是能直接看见、能 gitignore、容器重建不丢

## D-008 所有端口只绑 `127.0.0.1`

- **决策**：`"127.0.0.1:5432:5432"` 和 `"127.0.0.1:8000:8000"`
- **理由**：默认不把数据库和 API 暴露到局域网。开发阶段没有任何理由让同网络的其他人访问
- **代价**：无法用手机在同一 WiFi 下预览（需要时临时改）
- **将来对外开放**：V2 阶段加反向代理 + HTTPS，而不是直接改端口绑定

## D-011 采用全异步数据库访问（SQLAlchemy async + asyncpg）—— 已决定

- **背景**：M1 开始引入 ORM，这个决定会贯穿所有后续代码
- **决策**：**全异步**。`create_async_engine` + `AsyncSession` + `asyncpg`，迁移用 Alembic 的 async 模板
- **理由**：
  1. 项目核心是 AI。一次模型调用是数秒级 I/O 等待，同步会把线程全程占住
  2. FastAPI 生态（LLM SDK、httpx）原生 async，混用要时刻提防"在 async 里调用同步阻塞代码"，而那种错误会卡死整个事件循环
  3. 若先做同步，M4 做 RAG 时要返工所有 repository 函数 + endpoint + Alembic 配置
- **代价**：
  1. 关系属性**不能懒加载**，必须 `selectinload()` 显式预加载，否则报 `MissingGreenlet`
  2. `AsyncSession` 不能跨协程共享，必须"每请求一个 session"
  3. Alembic 要用 `-t async` 模板，并在 `env.py` 里处理 `run_sync`
- **替代方案**：同步 + `psycopg` —— 更接近作者的 Spring 经验、上手更快。否决原因：作者目标是"学对 + 不走回头路"，而不是最快看到结果
- **状态**：**已决定（2026-10-19）**

## D-012 学习心得日志只留本地，不公开

- **背景**：仓库是 public，而 `docs/journal/` 里要写大量个人思考、联想、甚至不确定的想法
- **决策**：`docs/journal/*.md` 加入 `.gitignore`，只保留 `README.md`（写作规范）进库
- **理由**：公开的仓库适合放"结论"和"可交付物"，不适合放"未成形的思考"。写心得时如果时刻想着"这是公开的"，会自我审查，反而写不出真实的东西
- **代价**：失去"展示学习过程"这个作品集加分项
- **补偿方式**：需要展示时，可以挑单篇用 `git add -f` 强制加入，或把提炼后的结论写进 `docs/handoff/`

## D-013 ruff 规则集显式声明，并忽略"形近字符"类规则

- **背景**：一次 CI 失败暴露 56 个 lint 错误。其中 14 个是真实问题（import 排序、过时语法、`Depends` 默认参数），另外 53 个是 `RUF002/RUF003` 在抱怨中文全角标点
- **决策**：
  1. **显式声明** `select = ["E", "F", "I", "UP", "B", "RUF"]`，不依赖 ruff 默认值
  2. `extend-exclude = ["alembic/versions"]` —— Alembic 生成的迁移文件不参与风格检查
  3. `ignore = ["RUF001", "RUF002", "RUF003"]` —— 注释与文档字符串使用中文，全角标点是正确书写
  4. 依赖注入统一用 `Annotated[AsyncSession, Depends(get_session)]`，避免 `B008`
- **理由**：
  - 默认值会随 ruff 版本变化。某天升级 ruff 突然爆一堆错，你无法判断是自己改坏了还是规则变了
  - 生成代码不是我们写的，用我们的风格规则去要求它没有意义
  - `RUF001-003` 假设"代码里只有英文"，其真实目的是防止西里尔字母伪装拉丁字母（安全攻击）。中文项目不适用
- **代价**：中文注释的代码在纯英文团队里会显得不一致
- **替代方案**：把 Python 注释全部改成英文 —— 否决。注释是学习产物，中文表达更精确；且 `docs/` 全为中文，混排反而割裂
- **副作用记录**：`RUF100`（无用 noqa）很有价值，它一次性发现 3 个"防根本不存在的错"的安慰剂注释
- **状态**：**已决定（2026-10-21）**
